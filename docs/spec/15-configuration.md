# 15. Конфигурация и локальная разработка

### 15.1 Переменные окружения

Читаются из окружения и файла `.env` (pydantic-settings, `src/meetup_bot/config.py`). Шаблон с комментариями — `.env.example`.

| Переменная | Обязательна | Пример | Описание |
|---|:-:|---|---|
| `BOT_TOKEN` | да | `123:ABC…` | Токен из BotFather. Проверяется формат `<число>:<строка>` |
| `OWNER_IDS` | да | `111111,222222` | Telegram ID владельцев через запятую, хотя бы один. Владельцы всегда админы и единственные, кто назначает админов |
| `SERVICE_CHAT_ID` | да | `-100123…` | Служебный чат: отдельная закрытая группа (владелец, бот, ответственные ведущие). Бот должен в нём состоять |
| `DATABASE_URL` | нет | `sqlite+aiosqlite:///./data/bot.db` | По умолчанию — значение из примера. В Docker `compose.yaml` задаёт `sqlite+aiosqlite:////app/data/bot.db` |
| `ENV` | нет | `dev` / `prod` | По умолчанию `prod`. В `dev` бот показывает ID пользователя на `/start` и ID чата при добавлении в группу, работает `/dev_shift` (15.4) |
| `LOG_LEVEL` | нет | `INFO` | Уровень логов |
| `SENTRY_DSN` | нет | | Отчёты об ошибках в Sentry; пусто — выключено |
| `APP_VERSION` | нет | `a1b2c3d` | Версия в сообщении «Бот запущен»; если не задана — версия пакета. Задумана для `deploy.yml` (17.4) |

При неполной или неверной конфигурации бот завершается с кодом 2 и перечисляет проблемные переменные без их значений; если Telegram отклонил токен или недоступен — код 1.

Секреты **никогда** не коммитятся. В репозитории лежит только `.env.example`. Боевой токен хранится только в `.env` на сервере (права 600).

### 15.2 Как узнать свой Telegram ID и ID чата

ID пользователей и чатов общие для всех ботов, поэтому их узнают тестовым ботом с `ENV=dev`:

- написать боту `/start` — в ответе будет «ID пользователя: …»;
- добавить бота в группу — он напишет в неё «ID этого чата: …».

В любом режиме при добавлении в группу бот пишет в лог `бот добавлен в чат: chat_id=…` (событие `my_chat_member`). Пошагово — [README](../../README.md#3-как-узнать-свой-telegram-id-и-id-служебного-чата), раздел 3.

### 15.3 Первый запуск

```bash
git clone https://github.com/dimbo1324/meetup-rsvp-bot.git && cd meetup-rsvp-bot
uv run python dev.py setup    # uv sync, .env из .env.example, pre-commit-хуки
# вписать в .env СВОЙ тестовый токен, OWNER_IDS, SERVICE_CHAT_ID, ENV=dev
uv run python dev.py run      # alembic upgrade head + python -m meetup_bot
```

Python 3.14 uv ставит сам. Остальные команды — `uv run python dev.py list`.

### 15.4 Тестовое окружение

- У каждого разработчика **свой тестовый бот** в BotFather (8.7), настроенный как боевой (Приложение А).
- Общая тестовая группа (2–3 чата, чтобы проверять рассылку в несколько чатов) с разработчиками и 1–2 добровольцами. Сценарии ручной проверки — [`docs/telegram-test-checklist.md`](../telegram-test-checklist.md).
- Для проверки сценариев с «временем» есть админская dev-команда `/dev_shift <минуты>`. Она сдвигает виртуальные часы (`Clock`) и работает **только** при `ENV=dev`. Сдвиг хранится в памяти и сбрасывается при перезапуске.

### 15.5 Как работаем в Git

- В `main` работает только владелец; остальные (люди и AI-ассистенты) работают в ветках `feat/…`, `fix/…`, `chore/…`, `docs/…` и вливают их fast-forward слиянием после зелёного `quality-gate` (подробно — `CONTRIBUTING.md`).
- Коммиты в стиле Conventional Commits, по-русски (`feat: запись +1`).
- Вехи и статус — `docs/ROADMAP.md`, решения и открытые вопросы — `docs/open-questions.md`.

### 15.6 Несколько локаций

Каждая локация — отдельная установка со своим `.env` (свой `BOT_TOKEN`, `OWNER_IDS`, `SERVICE_CHAT_ID`) и своим каталогом данных. Переменных для выбора локации нет: код не знает о локациях. Подробно — 17.8.
