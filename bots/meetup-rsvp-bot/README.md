# meetup-rsvp-bot

Telegram-бот, через который записываются на еженедельные встречи русскоязычного сообщества в
Монтевидео. Мест на встрече немного, обычно десять, и раньше их считали вручную по сообщениям
«я приду» в чате. Теперь человек нажимает кнопку под постом, а бот сам ведёт список, держит лимит,
ставит лишних в очередь и напоминает о встрече.

## Как это работает

Ведущий набирает в чате сообщества `@имябота`, выбирает встречу, и в чат уходит пост с кнопками
«Записаться» и «Отменить запись». Один и тот же пост можно разослать в несколько чатов: счётчик
мест у всех копий общий и обновляется сам. Сам бот в чаты сообщества ничего не пишет и в них не
состоит, он живёт только в закрытом служебном чате ведущих.

Ниже описано поведение с настройками по умолчанию: встреча по пятницам с 16:30 до 18:30, время
Монтевидео. Всё это ведущий меняет в боте через `/menu` → ⚙️ Настройки, программист для этого
не нужен.

**Участник** видит в посте только счётчик «Записались: 7 из 10», чужих имён там нет. Записаться
можно и после начала встречи, пока запись не закрылась (через час после начала) и есть свободные
места. Если мест нет, человек встаёт в очередь и получает место, как только кто-то откажется.
Отменить запись самому можно до 20:00 накануне, дальше только через ведущего. Кто записался и не
пришёл, после первой же неявки больше записываться не может, пока ведущий не снимет бан. Если
нажать у бота «Старт», он будет присылать в личку напоминания и сообщать, когда освободилось
место.

**Ведущий** управляет всем в личке с ботом через `/menu`: встречи, участники, чёрный список,
настройки и тексты сообщений. Полный список записавшихся и выгрузку в Excel видят только ведущие.
Назначать других ведущих может только владелец.

**Что бот делает сам, без участия людей:**

- в субботу в 10:00 создаёт встречу на следующую пятницу и пишет об этом в служебный чат;
- в среду в 10:00 напоминает там же, если пост ещё никто не разослал;
- в четверг за сутки до встречи напоминает записавшимся (тем, кто нажимал «Старт»);
- в пятницу в 17:30 закрывает запись и присылает ведущим итоговый список;
- в 18:00 присылает каждому ведущему список для отметки явки;
- каждую ночь в 04:00 делает копию базы и отправляет её файлом в служебный чат.

Из чатов бот никого не удаляет: бан означает только то, что человек не может записаться.

## 1. Запуск на своём компьютере

Так бота запускают при разработке и для проверки в тестовой группе. Понадобятся
[Git](https://git-scm.com/) и [uv](https://docs.astral.sh/uv/), а Python 3.14 uv поставит сам.

```bash
git clone https://github.com/dimbo1324/meetup-rsvp-bot.git
cd meetup-rsvp-bot
uv run python dev.py setup      # зависимости, .env из шаблона и pre-commit-хуки
```

Дальше откройте `.env` и заполните его, внутри у каждой строки есть пояснение. Самое важное:

- `BOT_TOKEN` — токен **вашего тестового бота** (как его получить, в разделе 2). Один токен можно
  запустить только в одном месте: если он работает где-то ещё, две копии бота будут отбирать друг
  у друга сообщения. Токен боевого бота на своём компьютере не используйте никогда.
- `OWNER_IDS` и `SERVICE_CHAT_ID` — где их взять, в разделе 3.
- `ENV=dev` — в этом режиме бот показывает ID и понимает команду `/dev_shift`, которой удобно
  «перематывать» время при проверке напоминаний.

```bash
uv run python dev.py run        # обновит базу до последней версии и запустит бота
```

База появится в `data/bot.db`, остановить бота можно через `Ctrl+C`. Если в `.env` чего-то не
хватает, бот сразу завершится с кодом 2 и напишет, какой переменной нет (сами значения он не
печатает). Если Telegram не принял токен или нет связи, код выхода будет 1. Проверить, всё ли
установлено, можно командой `uv run python dev.py doctor`.

### Что лежит в `.env`

| Переменная | Нужна | Что это |
|---|:-:|---|
| `BOT_TOKEN` | да | Токен из @BotFather вида `123456789:AA…` |
| `OWNER_IDS` | да | Telegram ID владельцев через запятую, без пробелов, хотя бы один |
| `SERVICE_CHAT_ID` | да | ID закрытой служебной группы, куда добавлен бот |
| `DATABASE_URL` | нет | Путь к базе SQLite; в Docker его задаёт `compose.yaml` |
| `ENV` | нет | `prod` (по умолчанию) или `dev`, в котором бот показывает ID и понимает `/dev_shift` |
| `LOG_LEVEL` | нет | `DEBUG`, `INFO` (по умолчанию), `WARNING` или `ERROR` |
| `SENTRY_DSN` | нет | Адрес Sentry для отчётов об ошибках; если пусто, отчёты не отправляются |
| `APP_VERSION` | нет | Версия, которую бот пишет при запуске; при сборке образа подставляется сама (раздел 4.6) |

Подробнее о настройке — в [разделе 15 спецификации](docs/spec/15-configuration.md).

## 2. Регистрация бота в @BotFather

Это делается один раз для каждого бота: и для тестового, и для боевого. Откройте
[@BotFather](https://t.me/BotFather) и пройдите по командам:

| Команда | Что выбрать | Зачем |
|---|---|---|
| `/newbot` | Имя (его видят все) и username, который заканчивается на `bot` | BotFather выдаст токен, это и есть `BOT_TOKEN`. Никому его не пересылайте |
| `/setinline` | Выбрать бота и ввести подсказку `Выберите встречу…` | Это включает режим, в котором ведущий рассылает пост, набирая `@имябота` в чате |
| `/setinlinefeedback` | **Enabled** | **Обязательно.** Без этого бот не узнает о разосланных постах и не сможет обновлять в них счётчик |
| `/setjoingroups` | **Enable** | Чтобы бота можно было добавить в служебный чат. Потом можно вернуть Disable, и посторонние не смогут добавить бота к себе |
| `/setprivacy` | Оставить **Enabled**, как есть | Читать переписку в группах боту не нужно |
| `/setdescription`, `/setabouttext`, `/setuserpic` | Например, «Бот для записи на встречи сообщества» и аватарку | По желанию: это люди увидят в профиле бота |

Список команд (`/start`, `/menu` и другие) бот выставляет сам при запуске, так что `/setcommands`
не нужен. Если токен случайно утёк, отзовите его командой `/revoke` в @BotFather, впишите новый
в `.env` и перезапустите бота.

## 3. Где взять свой ID и ID служебного чата

ID людей и чатов в Telegram одинаковые для всех ботов, поэтому проще всего узнать их тестовым
ботом, запущенным у себя с `ENV=dev`. Чтобы он вообще стартовал, временно впишите в `.env`
заглушки `OWNER_IDS=1` и `SERVICE_CHAT_ID=0`.

1. **Свой ID.** Напишите боту в личку `/start`, в ответе будет строка «ID пользователя: …».
   Это число и есть ваш `OWNER_IDS`. Владельцев может быть несколько, через запятую.
2. **ID служебного чата.** Создайте закрытую группу только для ведущих и добавьте туда бота.
   Он сам напишет в группу «ID этого чата: …». Это `SERVICE_CHAT_ID`, обычно отрицательное
   число, а у супергрупп оно начинается с `-100`.
3. Остановите бота, впишите настоящие значения и удалите тестовую базу `data/bot.db`: заглушка
   из `OWNER_IDS` успела записаться туда как владелец. После перезапуска в служебном чате
   появится «Бот запущен, версия …».

Боевого бота добавьте в ту же служебную группу или в отдельную (её ID узнайте так же, тестовым
ботом). В боевом режиме бот ID не показывает, но пишет в лог строку
`бот добавлен в чат: chat_id=…`.

Учтите, что при некоторых изменениях настроек Telegram превращает группу в супергруппу, и её ID
меняется. Тогда сообщения в служебный чат перестают приходить, а в логе появляется «служебное
сообщение не доставлено». Узнайте новый ID и поправьте `.env`.

## 4. Установка на сервер

Боту хватает самого маленького сервера: 1 ГБ памяти и одно ядро, подойдёт и x86_64, и ARM.
Можно взять бесплатную машину Oracle Cloud Always Free или любой VPS за $4–5 в месяц; плюсы,
минусы и подводные камни разобраны в [разделе 17 спецификации](docs/spec/17-deploy-ops.md).
Входящие порты не нужны, бот сам ходит в Telegram, так что снаружи открыт только SSH.

Образ собирается прямо на сервере из этого репозитория. Автоматической выкладки из GitHub пока
нет, и для работы она не нужна.

Команды ниже для Ubuntu 24.04. Всё, что начинается с `sudo`, выполняет пользователь с правами
администратора (на Oracle это `ubuntu`).

### 4.1. Отдельный пользователь

```bash
sudo adduser --disabled-password --gecos "" deploy
sudo mkdir -p /home/deploy/.ssh
sudo cp ~/.ssh/authorized_keys /home/deploy/.ssh/
sudo chown -R deploy:deploy /home/deploy/.ssh
sudo chmod 700 /home/deploy/.ssh && sudo chmod 600 /home/deploy/.ssh/authorized_keys
```

Теперь под `deploy` можно заходить тем же SSH-ключом.

### 4.2. Docker

Ставим из официального репозитория Docker
([их инструкция](https://docs.docker.com/engine/install/ubuntu/)):

```bash
sudo apt-get update
sudo apt-get install -y ca-certificates curl git
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] \
https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo "$VERSION_CODENAME") stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo usermod -aG docker deploy
sudo apt-get install -y unattended-upgrades   # обновления безопасности будут ставиться сами
```

Кто состоит в группе `docker`, фактически имеет права root, поэтому кроме `deploy` туда никого
не добавляйте. Перезайдите под `deploy` и проверьте: `docker compose version`.

### 4.3. Код

```bash
sudo mkdir -p /opt/meetup-rsvp-bot
sudo chown deploy:deploy /opt/meetup-rsvp-bot
sudo -iu deploy
git clone https://github.com/dimbo1324/meetup-rsvp-bot.git /opt/meetup-rsvp-bot
cd /opt/meetup-rsvp-bot
```

Если репозиторий приватный, клонируйте его по SSH с ключом только на чтение
(GitHub → Settings → Deploy keys).

### 4.4. Файл `.env`

```bash
cp .env.example .env
chmod 600 .env
nano .env
```

Впишите:

```ini
BOT_TOKEN=<токен боевого бота>
OWNER_IDS=<ваш ID>
SERVICE_CHAT_ID=<ID служебного чата>
ENV=prod
LOG_LEVEL=INFO
```

`DATABASE_URL` трогать не нужно, в Docker его задаёт `compose.yaml`. Токен живёт только в этом
файле: не в git, не в GitHub и не в переписке.

### 4.5. Папка с данными

В контейнере бот работает не от root, а от пользователя с UID 10001, и папка с базой должна
принадлежать ему, иначе база не создастся:

```bash
mkdir -p data
sudo chown 10001:10001 data
sudo chmod 700 data
```

В `data/` будут лежать база `bot.db`, копии в `backups/` и служебный файл `heartbeat`.

### 4.6. Запуск

```bash
APP_VERSION=$(git rev-parse --short HEAD) docker compose up -d --build
```

`APP_VERSION` можно не указывать: это просто номер версии в сообщении «Бот запущен», по которому
потом видно, какой код работает. Первая сборка займёт несколько минут. При каждом старте
контейнер проверяет права на `data`, обновляет базу до нужной версии и только потом запускает
бота.

Привилегий у контейнера по минимуму: файловая система только для чтения (писать можно лишь в
`data/` и `/tmp`), пользователь не root, лишние права Linux отключены.

### 4.7. Проверка

```bash
docker compose ps                    # через минуту-две должно быть Up … (healthy)
docker compose logs --tail=50 bot    # строка «meetup-rsvp-bot …: запуск (prod)» и никаких ошибок
```

В служебном чате появится «Бот запущен, версия …». Если чат публичный или бот его не видит,
вместо этого или вместе с этим придёт предупреждение. Публичный чат не годится: туда уходят
копии базы с данными участников. Напоследок напишите боту в личку `/start`, и владельцу он
ответит приветствием с подсказкой про `/menu`.

Если контейнер всё время перезапускается (`Restarting`), загляните в логи:

- «Конфигурация неполная или неверная (.env): …» — исправьте указанную переменную;
- «Telegram отклонил BOT_TOKEN» — токен неверный или отозван;
- «Нет связи с Telegram» — проблема с сетью на сервере;
- «Каталог /app/data недоступен для записи пользователю бота» — пропущен шаг 4.5.

После правки `.env` перезапустите контейнер: `docker compose up -d --force-recreate`.
Логи хранятся в трёх файлах по 10 МБ, смотреть их вживую удобно так:
`docker compose logs -f bot`.

## 5. Первая настройка

Владелец пишет боту в личку `/start`, потом `/menu`. Дальше по шагам (подробно каждое окно меню
описано в [памятке ведущего](docs/admin-guide.md)):

1. **⚙️ Настройки → Встречи по умолчанию.** Укажите место (название кафе и адрес), ссылку на
   карту (`https://…`), описание и фото для поста. Проверьте день (пятница), время начала (16:30),
   длительность (120 минут) и число мест (10). Эти значения получат все **новые** встречи.
2. **⚙️ Настройки → Расписание** и **Правила.** Здесь, скорее всего, ничего менять не придётся:
   умолчания уже совпадают с тем, о чём договорились (отмена до 20:00 накануне, закрытие записи
   через час после начала, явка через полтора часа, бан после первой неявки).
3. **⚙️ Настройки → Часовой пояс** — `America/Montevideo`.
4. **📅 Встречи.** Встреча на ближайшую пятницу, возможно, уже есть: бот создаёт её сам, в том
   числе сразу после первого запуска (в служебном чате будет «Создана встреча: …»). Если она
   появилась раньше, чем вы заполнили шаг 1, откройте её карточку → ✏️ Редактировать и задайте
   место, описание и фото. Если встречи нет, создайте её: ➕ Новая встреча.
5. **👑 Админы** (эту кнопку видит только владелец). Добавьте остальных ведущих. Каждый из них
   должен хотя бы раз написать боту `/start`, иначе бот не сможет присылать ему список для
   отметки явки.
6. Убедитесь, что в каждом чате сообщества участникам разрешены inline-боты (как это проверить,
   есть [в памятке](docs/admin-guide.md#если-в-чате-запрещены-inline-боты)), и разошлите первый
   пост.

## 6. Обновление

На сервере под `deploy`:

```bash
cd /opt/meetup-rsvp-bot
git log -1 --date=iso-strict --pretty=format:"%h %cd %s"     # запомните коммит на случай отката
git fetch
git diff --name-only HEAD origin/main -- alembic/versions   # есть ли новые миграции базы
```

**Если последняя команда ничего не вывела**, миграций нет, и обновиться просто:

```bash
git pull
docker compose up -d --build
docker compose logs --tail=50 bot
```

**Если она вывела файлы миграций**, сначала сделайте копию базы руками, иначе откатиться потом
не получится:

```bash
git pull
docker compose build                       # пока собирается, старая версия продолжает работать
docker compose stop bot
mkdir -p ~/bot-backups
sudo cp data/bot.db ~/bot-backups/bot-before-update-$(date +%Y%m%d-%H%M).db
docker compose up -d
docker compose logs --tail=50 bot
```

Бот остановлен перед копированием, поэтому копия получится целой. Разосланные посты после
обновления продолжают работать как раньше.

## 7. Откат

```bash
cd /opt/meetup-rsvp-bot
git log -10 --date=iso-strict --pretty=format:"%h %cd %s"   # найдите последний рабочий коммит
git checkout <коммит>
docker compose up -d --build
```

Если в отменяемом обновлении не было миграций, этого достаточно. Если были, старый код не
запустится на изменённой базе: сначала восстановите копию, сделанную перед обновлением
(раздел 8.2), и только потом запускайте `docker compose up -d --build`. Записи, сделанные
после обновления, при этом пропадут.

Вернуться на свежую версию: `git checkout main && git pull && docker compose up -d --build`.

## 8. Бэкапы и восстановление

### 8.1. Как делаются копии

Каждую ночь в 04:00 по времени из настроек бот копирует базу в
`data/backups/bot-ГГГГ-ММ-ДД.db`, проверяет копию на целостность и хранит последние 14. Ту же
копию он отправляет файлом в служебный чат, чтобы она осталась, даже если сервер пропадёт
(файлы больше 50 МБ Telegram не принимает, тогда в логе будет предупреждение). Перед
обновлением с миграциями копию делают руками (раздел 6).

Раз в месяц полезно проверить, что из копии действительно можно подняться: скачайте её,
положите как `data/bot.db` и запустите бота у себя с `ENV=dev` и **тестовым** токеном.

В копиях лежат данные участников, поэтому за пределы служебного чата их не пересылайте.

### 8.2. Восстановление

1. Выберите копию: посмотрите `sudo ls -l /opt/meetup-rsvp-bot/data/backups/` или скачайте
   файл из служебного чата и закиньте на сервер (`scp bot-2026-11-01.db deploy@<сервер>:~/`).
   Если откатываетесь после обновления, берите ручную копию из `~/bot-backups/`.
2. Остановите бота и отложите текущую базу в сторону, не удаляя её:

   ```bash
   cd /opt/meetup-rsvp-bot
   docker compose stop bot
   OLD=data/replaced-$(date +%Y%m%d-%H%M)
   sudo mkdir -p "$OLD"
   for f in bot.db bot.db-wal bot.db-shm; do
     sudo test -e "data/$f" && sudo mv "data/$f" "$OLD/"
   done
   ```

   Файлы `bot.db-wal` и `bot.db-shm` — это журнал SQLite. Их тоже нужно убрать, иначе он
   смешается с восстановленной базой.
3. Положите копию на место и верните права:

   ```bash
   sudo cp data/backups/bot-2026-11-01.db data/bot.db    # или ~/bot-2026-11-01.db
   sudo chown 10001:10001 data/bot.db
   sudo chmod 600 data/bot.db
   ```

4. Запустите бота: `docker compose up -d`. Если копия старее кода, нужные миграции применятся
   при старте сами.
5. Проверьте `docker compose logs --tail=50 bot` и сообщение «Бот запущен» в служебном чате.
   В `/menu` → 📅 Встречи всё будет так, как было на момент копии. Посты в чатах обновятся при
   следующем изменении встречи.

## 9. Вторая локация

Если появится вторая площадка со своим ведущим, для неё запускается отдельная копия бота: свой
бот в @BotFather со своим токеном, своя база, свои владельцы, ведущие, настройки и чёрный
список. Код общий, и обе копии спокойно живут на одном сервере.

1. Заведите нового бота в @BotFather (раздел 2) и служебный чат для этой локации.
2. На сервере создайте `.env.<локация>` (например, `.env.punta`) по образцу `.env.example`, с
   правами 600, токеном **нового** бота, его владельцами, служебным чатом и `ENV=prod`.
3. Папка с данными: `mkdir data-punta && sudo chown 10001:10001 data-punta && sudo chmod 700 data-punta`.
4. В `compose.yaml` раскомментируйте шаблон `bot-<локация>` и замените `<локация>` на `punta`.
5. Запустите `docker compose up -d --build`. Проверка, обновление и бэкапы такие же, как для
   первой локации, только сервис называется `bot-punta` (`docker compose logs bot-punta`), а
   данные лежат в `data-punta`.

## 10. Команды для разработки

Всё рутинное делается через `dev.py`, полный список покажет `uv run python dev.py list`:

| Команда | Что делает |
|---|---|
| `doctor` | проверяет окружение: Python, uv, git, `.env`, `.venv`, pre-commit-хук |
| `setup` | ставит зависимости, создаёт `.env` из шаблона (если его нет), включает pre-commit-хуки |
| `run` | обновляет базу и запускает бота |
| `migrate` | только обновляет базу (`alembic upgrade head`) |
| `test` | запускает pytest; аргументы передаются дальше, например `dev.py test -k waitlist` |
| `format` / `lint` / `typecheck` | форматирует код и правит мелочи / проверяет без правок / запускает mypy |
| `quality-gate` | полная проверка перед слиянием: правила, зеркала, lint, mypy и все тесты |
| `sync-agents` | пересобирает `AGENTS.md` из `.ai/` (с `--check` только проверяет) |
