# План работ и прогресс: registro-civil-bot

Живой документ: **что запланировано, в каком порядке и что сделано**. Требования — `SPEC.md`
в корне бота (фазы — раздел 0.4, приёмка — раздел 8). Правила обновления —
`.ai/project/13-progress-tracking.md` монорепозитория.

Работа идёт **по этапам владельца** (решение R5 в `docs/open-questions.md`): этап объединяет
несколько фаз SPEC 0.4. **Как найти следующий этап:** первый этап в таблице §1 без статуса
«Готово». Внутри этапа фазы идут по порядку, каждая заканчивается коммитом; в конце этапа —
демонстрация владельцу и остановка до его ответа.

## 2. Этапы подробно

### Э0. Подготовка репозитория

**Статус.** Готово 2026-11-11. Поставлено: каталог `bots/registro-civil-bot/` в монорепозитории
(контракт — `docs/monorepo.md` корня), зависимости из SPEC.md 2.1 в общем `uv.lock` (версии
совпадают с таблицей ТЗ), пакет `rcbot` (только `__init__.py`), Chromium для Playwright в
`.browsers/` (команда `dev.py setup`), `SPEC.md` без номеров заявки (решение R1), правила бота
для ассистентов (`CLAUDE.md`, `.ai/`, агенты `rcbot-*`), дымовой тест стека
`tests/test_stack.py`. Проверено: Playwright 1.65 и greenlet ставятся на Python 3.14 под Windows
из готовых колёс, поэтому запасной путь D7 (отдельное окружение на 3.13) не нужен. Найдено и
вынесено владельцу: aioresponses несовместима с aiohttp 3.14 (Q-M3, закрыт решением R7), браузеры
занимают 741 МБ против критерия 8 «папка < 300 МБ» (Q-M2, закрыт решением R8).

### Э1. Бизнес-логика

Читать: SPEC.md 2–3, `docs/architecture/invariants.md`. Порядок фаз: P1 каркас (конфиг,
секреты через keyring, логи с `RedactionFilter`, БД и миграции, CLI) → P2 вход (Playwright,
cookies в aiohttp) → P3 источники (`DomSource` по селекторам SPEC 1.3; `ApiSource` с портом,
обработкой ошибок, карантином и моделью ответа-заглушкой — формат API станет известен только
после разведки в Э3) → P4 детектор и инциденты → P5 уведомления → P6 Telegram-интерфейс → P7
надёжность (один экземпляр, защита от сна, очистка, «сторож», скрипты Планировщика). Живой сайт,
реальные токены и внешние сервисы не трогаем. Тесты — в Э2; дымовой тест стека остаётся зелёным.

**Статус.** Готово 2026-11-11, коммит на каждую фазу. Поставлено (подробно —
`docs/architecture/overview.md`): P1 — настройки с жёстким минимумом 10 с, секреты в keyring,
пути от каталога бота, домен, логи с `RedactionFilter`, Sentry выключен, SQLite в WAL и миграция
`0001`, репозитории, `rcbot init` и `doctor`; P2 — вход через ID Uruguay в Playwright без
профиля, `SessionManager` (≤ 6 входов в час, D5), `rcbot login --check`; P3 — `DomSource`,
каркас `ApiSource` с карантином, `SaeSource` выключен, `rcbot discover` с очисткой до записи,
`rcbot check --once`; P4 — детектор, шина событий, учёт инцидентов, `PollLoop` (лестница D4,
отступление, `NEEDS_MANUAL`, переход на `DomSource`), настройки в `kv_settings`; P5 — Telegram,
ntfy, CallMeBot параллельно, повторы до «Вижу», прогрев; P6 — Telegram-интерфейс только для
владельца, команды и меню; P7 — один экземпляр, защита от сна, очистка, отчёт, «сторож»,
супервизор, `run`, `simulate`, `purge`, `uninstall`, скрипты Планировщика. Проверено без сети
(тесты — Э2): `DomSource`, цикл опроса, рассылка, хранение, миграция, Telegram-интерфейс. Не сделано по плану: разбор ответа API (нужен дамп
разведки, Э3), чтение SAE (D6). Что бот пока видит только дни без времени и
опрашивает не чаще раза в минуту — следствие `DomSource`, см. обзор.

Доработка по указанию владельца (2026-11-11, решение R6): журнал наблюдения на рабочем столе —
каждая проверка, каждое действие, окна записи (`openings.csv`), состояние и признак «жив /
завис» (`status.json`), квота 10 → 5 ГБ с удалением старых дней во время работы; таймаут
проверки 150 с и монитор живости с автоматическим перезапуском цикла опроса и браузера.
Проверено на синтетическом сценарии (запись, вырезание номеров, квота, зависание).

### Э2. Тесты

Читать: SPEC.md 7, 3.4; `docs/testing.md`.

**Статус.** Готово 2026-11-12. Поставлено: тесты (после Q-M4 — без ожидаемых падений) в
`tests/unit|integration|e2e|privacy|architecture`; покрытие `domain` и `application` выше
порога 85 %, порог проверяет полный прогон `dev.py test`. Фальшивые часы, локальный HTTPS-сервер
(`trustme`), настоящие SQLite и Chromium на локальных страницах, фальшивые каналы и Telegram;
девять сквозных сценариев SPEC 7 и замеры скорости; приватность и архитектурные инварианты
проверены тестами. Найденные тестами ошибки исправлены с регрессионными тестами (пауза и
интервал, сортировка слотов, гонки журнала, cookies при сбросе сессии, номер этапа в БД, строгая
проверка хоста входа). Решения — R8, R9 в `docs/open-questions.md`. Не сделано по плану:
проверка на живом сайте и в реальных Telegram, ntfy, CallMeBot (этап 3).

Доработка после этапа (2026-11-12, указания владельца): быстрый старт под Windows 11 —
`scripts/quickstart.cmd` (и `quickstart.ps1`), короткий вызов `scripts/rcbot.cmd`, мастер
`rcbot init` спрашивает номер этапа и номер заявки и пишет их в `.env`; выбор браузера
`RCBOT_BROWSER` — Chrome → Edge → Chromium Playwright (решение R8); push ntfy без ссылки с номером
этапа (решение R10, закрыт Q-M4). Проверено тестами без сети; на живом сайте — этап 3.
