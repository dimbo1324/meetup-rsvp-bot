# Решения и открытые вопросы: registro-civil-bot

Решения D1–D8 по продукту — в `SPEC.md`, раздел 9; там же сказано, что открытых вопросов по
ТЗ нет. Здесь — решения, принятые при размещении бота в монорепозитории, и новые вопросы.
Решение, ограничивающее будущую работу, попадает сюда, а не остаётся в чате.

## Решения

**R1. Обезличенная копия ТЗ (2026-11-11, при подготовке репозитория).** В `SPEC.md` в
репозитории номер заявки и номер этапа владельца заменены метками `<НОМЕР_ЗАЯВКИ>` и
`<НОМЕР_ЭТАПА>`: они связывают репозиторий с личным делом владельца, а git-история
публикуется на GitHub. Реальные значения — только в локальном `bots/registro-civil-bot/.env`
(`RCBOT_AGENDA_URL` — номер этапа, `RCBOT_TRAMITE_ID` — номер заявки); код, тесты, фикстуры и
коммиты их не содержат. Других копий на ноутбуке нет: исходные файлы ТЗ с рабочего стола
удалены в Корзину по просьбе владельца 2026-11-11, их текст полностью совпадает с `SPEC.md`
с точностью до меток. Если `.env` потеряется, номера видны в «Bandeja de entrada» на bpmgob.

**R2. Корень бота — `bots/registro-civil-bot/` (2026-11-11).** SPEC.md 2.7 и 3.3 описывают
отдельную папку `%USERPROFILE%\Desktop\RegistroBot\`. В монорепозитории ею становится каталог
бота: там же лежат `data/`, `logs/`, `.browsers/`, `.cache/` (в `.gitignore` корня). «Все пути
от корня проекта» (`config/paths.py`) = от каталога бота. Вне каталога по-прежнему только
Credential Manager и задание Планировщика.

**R3. Окружение — общий `.venv` монорепозитория (2026-11-11).** `uv sync` ставит всех ботов в
`.venv` корня. Команды SPEC.md 4.2–4.7 (`uv sync`, `uv run rcbot …`) выполняются из корня
репозитория или через `dev.py`; `uv sync` из каталога бота сузил бы общее окружение до одного
бота. Путь к `pythonw.exe` для Планировщика (фаза P7) — `.venv\Scripts\pythonw.exe` корня, рабочий
каталог задания — каталог бота.

**R4. Проверки перед коммитом — через `dev.py` (2026-11-11).** Вместо `uv run ruff check`,
`uv run mypy`, `uv run pytest` из SPEC.md 6.4 — `uv run python dev.py quality-gate --bot
registro-civil-bot` (то же самое плюс синхронизация правил и раскладка монорепозитория).

**R5. Порядок работ — пять этапов владельца (2026-11-11, указание владельца).** Вместо
последовательности фаз SPEC 0.4 с демонстрацией после каждой работа идёт этапами:
1. **Бизнес-логика** — весь код фаз P1–P7 без живого сайта и реальных токенов;
2. **Тесты** — максимальное покрытие на синтетических данных, без подключений;
3. **Подключение** — шаги, которые делает владелец: бот в Telegram, ntfy, CallMeBot, секреты,
   вход для разведки, автозапуск и питание ноутбука;
4. **Аудит** — проверка, что всё подключено и работает (критерии SPEC 8);
5. **Работа** — бот работает круглосуточно, ноутбук постоянно включён и в сети.

Следствия, принятые вместе с решением: разведка P0 (нужен вход владельца) переносится в этап 3,
поэтому на этапе 1 `DomSource` делается полностью, а у `ApiSource` — каркас, разбор ответа
пишется после дампа на этапе 3 (D1 это допускает). Тесты отделены от кода: на этапе 1 при
каждом коммите обязательны ruff, `mypy --strict`, `check-layout` и зелёный дымовой тест, а
покрытие ≥ 85 % — критерий этапа 2. Коммит — после каждой фазы, демонстрация и остановка — в
конце этапа. Сводка — `docs/ROADMAP.md`, §1.

## Открытые вопросы

- **Q-M4. Ссылка на заявку в ntfy (решить до этапа 3).** SPEC 2.4 велит класть в push ntfy поле
  `click` со ссылкой на шаг «Agenda»; ссылка содержит номер этапа, а ntfy — сторонний сервис
  (SPEC 2.4, «Приватность каналов»). Сделано по SPEC 2.4. Вариант строже: без `click` — по
  нажатию на push откроется только приложение ntfy, ссылка останется в Telegram.
- **Q-M3. aioresponses несовместима с aiohttp 3.14 (решить до этапа 2).** SPEC.md 2.1 называет
  aioresponses для тестов, но последняя версия 0.7.9 (2026-06-23) падает на aiohttp 3.14.5:
  `ClientResponse.__init__()` требует `stream_writer`. Тест `test_stack.py` фиксирует это
  через `xfail(strict=True)` и упадёт, когда библиотеку починят. Варианты: (а) все HTTP-тесты
  на фальшивом сервере `aiohttp.test_utils.TestServer` — он уже нужен для интеграционных тестов
  SPEC 7, работает (дымовой тест зелёный) и не требует зависимостей; (б) ждать исправления
  aioresponses; (в) опустить aiohttp ниже 3.14 — против SPEC 2.1. Рекомендация — (а) и убрать
  aioresponses из зависимостей.
- **Q-M2. Размер браузера и критерий приёмки 8 (решить до этапа 3).** `playwright install chromium`
  ставит в `.browsers/` 741 МБ: Chromium с окном (451 МБ) и `chromium-headless-shell`
  (287 МБ). Критерий 8 SPEC.md требует, чтобы папка бота была меньше 300 МБ вместе с Chromium.
  Окно нужно только `rcbot discover` (фаза P0); вход и `DomSource` работают без окна
  (`RCBOT_HEADLESS=true`). Рекомендация: в `setup` ставить только `--only-shell` (287 МБ), а
  `discover` открывать в уже установленном системном Edge (`channel="msedge"`), который не
  занимает места в папке бота. Пока стоит полный набор, чтобы P0 не упёрся в отсутствие браузера.
- **Q-M1. Проверка на Windows в CI.** Бот работает только на Windows; в CI добавлено задание
  `windows-latest` для этого бота. Если GitHub-минуты станут ограничением — решить, оставлять ли
  его на каждый PR.
