# Решения и открытые вопросы: registro-civil-bot

Решения D1–D8 по продукту — в `SPEC.md`, раздел 9; там же сказано, что открытых вопросов по
ТЗ нет. Здесь — решения, принятые при размещении бота в монорепозитории, и новые вопросы.
Решение, ограничивающее будущую работу, попадает сюда, а не остаётся в чате.

## Решения

**R1. Обезличенная копия ТЗ (2026-11-11, при подготовке репозитория).** В `SPEC.md` в
репозитории номер заявки и номер этапа владельца заменены метками `<НОМЕР_ЗАЯВКИ>` и
`<НОМЕР_ЭТАПА>`: они связывают репозиторий с личным делом владельца, а git-история
публикуется на GitHub. Реальные значения — только в локальном `bots/registro-civil-bot/.env`
(`RCBOT_AGENDA_URL` — номер этапа, `RCBOT_TRAMITE_ID` — номер заявки); код, тесты, фикстуры и
коммиты их не содержат. Других копий на ноутбуке нет: исходные файлы ТЗ с рабочего стола
удалены в Корзину по просьбе владельца 2026-11-11, их текст полностью совпадает с `SPEC.md`
с точностью до меток. Если `.env` потеряется, номера видны в «Bandeja de entrada» на bpmgob.

**R2. Корень бота — `bots/registro-civil-bot/` (2026-11-11).** SPEC.md 2.7 и 3.3 описывают
отдельную папку `%USERPROFILE%\Desktop\RegistroBot\`. В монорепозитории ею становится каталог
бота: там же лежат `data/`, `logs/`, `.browsers/`, `.cache/` (в `.gitignore` корня). «Все пути
от корня проекта» (`config/paths.py`) = от каталога бота. Вне каталога по-прежнему только
Credential Manager и задание Планировщика.

**R3. Окружение — общий `.venv` монорепозитория (2026-11-11).** `uv sync` ставит всех ботов в
`.venv` корня. Команды SPEC.md 4.2–4.7 (`uv sync`, `uv run rcbot …`) выполняются из корня
репозитория или через `dev.py`; `uv sync` из каталога бота сузил бы общее окружение до одного
бота. Путь к `pythonw.exe` для Планировщика (фаза P7) — `.venv\Scripts\pythonw.exe` корня, рабочий
каталог задания — каталог бота.

**R4. Проверки перед коммитом — через `dev.py` (2026-11-11).** Вместо `uv run ruff check`,
`uv run mypy`, `uv run pytest` из SPEC.md 6.4 — `uv run python dev.py quality-gate --bot
registro-civil-bot` (то же самое плюс синхронизация правил и раскладка монорепозитория).

**R5. Порядок работ — пять этапов владельца (2026-11-11, указание владельца).** Вместо
последовательности фаз SPEC 0.4 с демонстрацией после каждой работа идёт этапами:
1. **Бизнес-логика** — весь код фаз P1–P7 без живого сайта и реальных токенов;
2. **Тесты** — максимальное покрытие на синтетических данных, без подключений;
3. **Подключение** — шаги, которые делает владелец: бот в Telegram, ntfy, CallMeBot, секреты,
   вход для разведки, автозапуск и питание ноутбука;
4. **Аудит** — проверка, что всё подключено и работает (критерии SPEC 8);
5. **Работа** — бот работает круглосуточно, ноутбук постоянно включён и в сети.

Следствия, принятые вместе с решением: разведка P0 (нужен вход владельца) переносится в этап 3,
поэтому на этапе 1 `DomSource` делается полностью, а у `ApiSource` — каркас, разбор ответа
пишется после дампа на этапе 3 (D1 это допускает). Тесты отделены от кода: на этапе 1 при
каждом коммите обязательны ruff, `mypy --strict`, `check-layout` и зелёный дымовой тест, а
покрытие ≥ 85 % — критерий этапа 2. Коммит — после каждой фазы, демонстрация и остановка — в
конце этапа. Сводка — `docs/ROADMAP.md`, §1.

**R6. Журнал наблюдения на рабочем столе (2026-11-11, указание владельца).** Кроме логов в
каталоге бота (SPEC 2.7), бот ведёт журнал в папке `rcbot-journal` на рабочем столе (путь —
`RCBOT_JOURNAL_DIR`): каждая проверка (`checks/`), каждое действие и событие (`events/`),
подробный текстовый лог (`logs/`), появления и пропажи мест (`openings.csv`), текущее состояние
и признак «жив / завис» (`status.json`). Это отступление от SPEC 2.7 («вне папки бота — только
Credential Manager и Планировщик») и от правила «каждая проверка не пишется в БД»: проверки
пишутся в файлы журнала, БД по-прежнему хранит только почасовую статистику. Квота: больше
`RCBOT_JOURNAL_MAX_GB` (10 ГБ) → удаляются самые старые дни до `RCBOT_JOURNAL_TRIM_TO_GB`
(5 ГБ), проверка при старте и каждые 10 минут; сегодняшние файлы, `status.json` и
`openings.csv` не удаляются. Приватность прежняя: всё проходит через фильтр вырезания, номера
заявки и этапа заменяются на `***`. Вместе с журналом — защита от зависания: проверка дольше
150 с прерывается, монитор живости перезапускает цикл опроса и браузер и сообщает владельцу.

**R7. Инструменты тестов (2026-11-11; закрывает Q-M3).** HTTP-тесты идут к настоящему локальному
HTTPS-серверу aiohttp с сертификатом `trustme` (`tests/fakes.py::LocalTlsServer`), а не через
подмену клиента: так проверяются реальные сокеты, TLS, таймауты и переадресации. `aioresponses`
из зависимостей убрана (0.7.9 несовместима с aiohttp 3.14.5). Добавлены `hypothesis` (свойства),
`trustme` (локальный TLS), `pytest-timeout` (зависший тест не вешает прогон). `SafeHttp` получил
необязательный `ssl_context` для тестов; в работе проверка сертификатов по системным центрам
действует всегда, отключить её нельзя. Порог покрытия 85 % для `domain` и `application` проверяет
полный прогон (`[tool.monorepo].coverage` в `pyproject.toml` бота). Подробно — `docs/testing.md`.

**R8. Браузер: любой, первым — Google Chrome (2026-11-12, указание владельца).** Бот обязан
работать с любым браузером на движке Chromium, первоочередной — установленный Google Chrome.
Порядок выбора по умолчанию: Chrome → Edge → встроенный Chromium Playwright (только если
ничего из установленного не найдено). Реализовано 2026-11-12: настройка `RCBOT_BROWSER` (`auto`, `chrome`, `msedge`, `chromium`;
явный выбор без запасных вариантов), `rcbot doctor` показывает найденные браузеры, `rcbot discover`
идёт в выбранном браузере (`RCBOT_DISCOVER_CHANNEL` заменена). Проверено настоящими Chrome 157 и
Edge 157 на локальной странице. Firefox и Safari не поддерживаются:
целевая ОС — Windows 11 (указание владельца того же дня), и Chrome с Edge покрывают задачу.
Следствие: если Chrome или Edge есть, Chromium Playwright (741 МБ) не нужен, это закрывает Q-M2
(размер `.browsers/` против критерия 8 SPEC «папка бота < 300 МБ»): быстрый старт ставит Chromium
только при отсутствии обоих браузеров. `dev.py setup` по-прежнему ставит Chromium (нужен тестам и
запасной ветке `auto`); отказ от этого шага — отдельное решение.

**R9. Итоги этапа 2 (2026-11-12).** Тесты — в `tests/unit|integration|e2e|privacy|architecture`;
в полном прогоне покрытие `domain` и `application` выше порога 85 %. Сквозные сценарии
идут на локальных страницах и фальшивых каналах без сети. Решения, принятые по находкам тестов:
- пауза `/pause` ограничена годом (`MAX_PAUSE_MINUTES`), `/pause 0` — отказ (бессрочная пауза —
  через меню «до /resume»); интервал NaN и бесконечность отклоняются;
- после входа и команд владельца цикл опроса соблюдает минимум между проверками (`_not_before`),
  поэтому «мгновенной» перепроверки сразу после входа нет;
- запись журнала по умолчанию фоновая (`RCBOT_JOURNAL_BACKGROUND=true`), в тестах выключена;
- cookies `SafeHttp` живут дольше его сессии: сброс зависшего источника не тратит вход;
- ntfy без отдельного текста для push шлёт общую фразу, а не текст тревоги;
- номер этапа не попадает в БД: в таблице целей хранится только хост;
- страница входа определяется строгим сравнением хоста (`is_login_url`).

**R10. ntfy без ссылки click (2026-11-12, решение владельца; закрывает Q-M4).** Из push ntfy
убрано поле `click`: ссылка на шаг «Agenda» содержит номер этапа, а ntfy — сторонний сервис. Push
показывает только даты и общую фразу, по нажатию открывается приложение ntfy, ссылка остаётся в
тексте Telegram. Граница структурная: поле `Alert.click_url` удалено, передать ссылку в ntfy
больше нечем. SPEC 2.4 и таблица `Alert` приведены в соответствие. Цена: на одно нажатие больше.

## Открытые вопросы

- **Q-A1. Решения по итогам аудита 2026-11-13 (решает владелец).** Это не ошибки, а изменения
  поведения продукта; сделаны не были:
  - *Сеть браузера (SEC-5).* Playwright не подчиняется списку хостов: страница может грузить
    сторонние ресурсы, а адрес шага уходит в `Referer`. Ограничить запросы списком хостов можно,
    но нужные сайту статические хосты станут известны только на этапе 3.
  - *Источник SAE (D6).* Чтение SAE не реализовано, но флаг `RCBOT_SAE_SOURCE_ENABLED` добавляет
    `sae.mec.gub.uy` в список разрешённых хостов. Либо не расширять список, пока источника нет,
    либо убрать SAE целиком (`SaeSource`, `sae_url`, `UnconfirmedSlotsSeen`).
  - *Баннер «No hay cupos».* Поле `MonthView.no_slots_banner` разбирается, но не используется;
    возможно, оно задумано как подтверждение отсутствия мест.
  - *Валидатор номера заявки.* `RCBOT_TRAMITE_ID` проверяется только мастером (4–15 цифр); в
    `Settings` правило не введено, потому что тестовые значения вида `TEST-…` его бы не прошли.
  - *Единый пояс журнала.* `status.json` пишет моменты в UTC, `checks` и `events` — в местном
    поясе.
  - *`install.ps1`.* Во многом перекрывается `quickstart.ps1`; удалять только по решению владельца.
  - *Типизация `CheckRecord.state`.* Поле остаётся строкой: CLI пишет в него `check-once`.
  - *Вывод счётчика потерянных записей журнала.* `FileJournal.dropped` считается, но не показан
    в `status.json` и `/status`.
- **Q-M5. Оговорки этапа 2 для этапа 3 и 4.** Не проверено на живом сайте и в реальном Telegram,
  ntfy и CallMeBot (по плану это этап 3, `rcbot simulate`). Известные упрощения, решения по
  которым ждут практики:
  - лимит 6 входов в час хранится в памяти: при цикле перезапусков процесса он не действует;
  - `/relogin` в 10-минутной «тихой» паузе после тревоги откладывается (D5);
  - неверный пароль или отсутствие возврата на bpmgob дают `SiteUnavailable` после 60 с, а не
    `LoginFailed`; шаг входа называется в сообщении;
  - поллинг Telegram, упавший с исключением, перезапускается без уведомления владельца;
  - `report_text` считает типичную задержку приближённо (медиана медиан);
  - прогрев CallMeBot жёстко привязан к `api.callmebot.com`;
  - `DomSource` видит только дни без времени и опрашивает не чаще раза в 60 с до появления
    `ApiSource` (после разведки);
  - в CI на Linux тесты с Chromium пропускаются, на Windows они идут (см. `docs/testing.md`).
- **Q-M1. Проверка на Windows в CI.** Бот работает только на Windows; в CI добавлено задание
  `windows-latest` для этого бота. Если GitHub-минуты станут ограничением — решить, оставлять ли
  его на каждый PR.
